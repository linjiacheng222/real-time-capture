# 多路视频流与异步帧获取统一——落地计划

> 日期：2026-11-03。目标：把现有"active 单路连续流＋时间片多路"整合为**每路相机都是一等公民**的体系：任何接口（HTTP/WS/游戏指令/Java API）都能按相机 id 同步或异步获取帧流；异步帧获取（`grabFrame`）与多路渲染深度耦合（可指定相机、可指定位置临时渲一帧）。
> 现状基线：P2.3 v2（`b3ad5ca`）已有时间片多路＋`CameraFrameStore`＋HTTP 按 id；多监听器音频（`14bdef6`）已有按通道订阅。本计划补齐视频侧的对称能力。

---

## 一、差距清单（现状 → 目标）

| # | 差距 | 现状 | 目标 |
|---|---|---|---|
| G1 | FrameRequest 无 cameraId | 统一 capture 只能用 active/临时参数 | `cameraId` 可选字段：指定任意已存在相机 |
| G2 | WS 推流单路 | StreamPushService 硬编码 latest() | 按连接订阅相机集合，多路帧带 cameraId |
| G3 | grabFrame 不认相机 | 只接受临时参数新建相机 | 接受 cameraId（用该相机渲一帧）或参数（临时渲一帧） |
| G4 | 时间片帧率不可配 | 硬编码约 250ms 轮询 | `multi_camera_fps` 可配（每路目标帧率） |
| G5 | active 路与非 active 帧存储割裂 | active 走 VideoFrameBus，非 active 走 CameraFrameStore | 统一存储：全部进 CameraFrameStore（active 同时发 VideoFrameBus 保持兼容） |
| G6 | 游戏指令不能按相机截取 | `/captureapi capture` 只能 active/临时参数 | `camera:2` 参数指定相机 |
| G7 | 录像不能选相机之外的输入源 | recording 绑定 cameraId 但只读 primary | 录像可直接指定 `cameraId`（已部分支持，需与 G1 贯通） |
| G8 | WS 视频帧无 cameraId | 二进制帧头不含相机标识 | 帧头加 cameraId（新消息类型 0x04，含 magic，同音频 0x03 方案） |

## 二、设计决策

### D-1 统一帧出口（分层）

```
渲染层（生产者）
  OffscreenRenderPipeline（active 连续路）
  MultiCameraRenderer（时间片路）
        │ 全部发布到
        ▼
  CameraFrameStore.put(cameraId, frame)     ← 唯一帧存储（G5）
  VideoFrameBus.publish(frame)              ← 仅 active 路额外发（兼容 0x02 老消费者）
        │
消费层（按 id 取）
  HTTP  /camera/{id}/frame|stream            ← 已有，改读统一存储
  WS    video.subscribe + 0x04 帧           ← 新增（G2/G8）
  Java  CaptureApi.grabFrame(cameraId)      ← 改造（G3）
  统一  CaptureApi.capture(FrameRequest.cameraId)（G1/G6）
  录像  RecordingSession(cameraId)           ← 贯通（G7）
```

### D-2 时间片 → 按需调度（渐进）

v2 时间片保留为默认；新增 `multi_camera_fps`（0=关闭时间片，>0=每路目标帧率）。调度策略：
- 帧预算制：每帧 AFTER_LEVEL 总预算约 4ms（可配 `multi_camera_budget_ms`），在预算内按 round-robin 渲非 active 路；
- 某路有消费者（HTTP 轮询/WS 订阅/录像/异步 grab）时优先渲染该路；无消费者的路跳过（懒渲染）；
- 无任何多路消费者时 MultiCameraRenderer 整体挂起（零开销）。

### D-3 异步获取语义（grabFrame 耦合多路）

`CaptureApi.grabFrame` 双模式：
- **指定 cameraId**：排队等该相机的下一次渲帧（时间片或立即插队），返回该路帧——**不新建临时相机、不销毁**；
- **指定参数（无 cameraId）**：现行临时相机一帧即毁语义不变。

互斥规则不变：临时相机与流式同帧互斥；指定 cameraId 的 grabFrame 不受此互斥约束（它就是流式路的一部分）。

### D-4 0x04 视频帧线格式（对齐 0x03 音频方案）

```
[4B magic = 0x04 'C' 'A' 'P'][4B cameraId LE][8B timestamp][2B width][2B height][JPEG]
```
- 22B 头；magic 与 0x03 同族，客户端按首字节 0x03/0x04 分流；
- 订阅了多路的连接只收 0x04；仅订阅 active 单路的旧连接继续收 0x01 旧格式（向后兼容）。

## 三、任务分解（7 项，P0 核心 4 项 / P1 增强 3 项）

### V1（P0）统一帧存储与 FrameRequest.cameraId

改动：
- `OffscreenRenderPipeline.renderOffscreen`：编码后追加 `CameraFrameStore.put(spec.id(), frame)`（不删 VideoFrameBus.publish，双写过渡）；
- `MultiCameraRenderer`：已有 put，确认保留；
- `FrameRequest`＋`Builder.cameraId(Integer)`：非 null 时走"读取/触发该路"，null 时现行逻辑；
- `CaptureApi.captureFrame`：`request.cameraId() != null` → 直接从 `CameraFrameStore` 取（无帧则触发一次该路渲帧并等待，超时语义同现有 timeoutMillis）。

验收：HTTP `/camera/1/frame` 与 `/camera/0/frame` 在双相机下均返回各自的帧（时间戳/画面不同）。

### V2（P0）WS 多路订阅＋0x04 帧

改动：
- 新 `VideoSubscribeAction`：`{"action":"video.subscribe","params":{"cameras":[0,1,2]}}`；`video.unsubscribe`（空=全部）；
- 每连接维护 `Set<Integer> subscribedCameras`；
- `StreamPushService`：连接有订阅集合时，改推 0x04（从 CameraFrameStore 按 id 取，跳过无新帧的路——用每路上次推送时间戳判重）；无订阅时保持 0x01 旧行为；
- `MultiChannelVideoCodec`（新文件，对齐 MultiChannelAudioCodec）：encode/decode/hasMagic。

验收：一个 WS 连接同时订阅相机 1 和 2，收到两种 cameraId 的 0x04 帧；不订阅的连接只收 0x01。

### V3（P0）grabFrame 双模式（异步获取耦合多路）

改动：
- `VideoStreamHub.requestOneShot(int cameraId, long timeout)` 新重载：登记"等 cameraId 下一次帧"的等待者；`MultiCameraRenderer`/`OffscreenRenderPipeline` 每次编码后 `CameraFrameStore.put` 时唤醒等待者；等待期间把该路标记为"有消费者"（触发 V4 调度优先）；
- `CaptureApi.grabFrame(int cameraId, long timeoutMillis)` 新静态方法；
- 游戏指令 `/captureapi capture camera:2` → `FrameRequest.cameraId(2)` → 同步版走 captureFrame 路径。

验收：`/captureapi capture camera:2` 在相机 2 非 active 时返回相机 2 视角帧（画面与 `/camera/2/frame` 一致）。

### V4（P0）帧预算调度与懒渲染

改动：
- `CaptureConstants`/配置新增 `multi_camera_fps`（默认 4，0=关闭）、`multi_camera_budget_ms`（默认 4）；
- `MultiCameraRenderer`：维护每路 `lastRenderNanos`＋`hasConsumer`（HTTP 读取/WS 订阅/grabFrame 等待/录像＝消费者；CameraFrameStore 被读取即视为消费）；
- 调度：无消费者集合非空→跳过全部；有消费者→预算内 round-robin，超过 `multi_camera_fps` 间隔的路优先；
- `CameraFrameStore.get(id)` 顺带 `markConsumer(id, nowNanos)`（懒渲染信号）。

验收：无任何多路消费者时（只有 active 流），`multi_rendered` 计数不增长（零开销）；订阅相机 2 后帧率接近 `multi_camera_fps`。

### V5（P1）录像按相机贯通

- `RecordingParams.audioChannelId` 已有；补 `videoCameraId`（默认 0=active）；
- `RecordingSession` 读帧改从 `CameraFrameStore.get(videoCameraId)` 取（active 路双写保证兼容）；
- WS `recording.start` 加 `camera` 参数；游戏指令 `/captureapi record start camera:2`。

验收：相机 1 录像产物画面＝相机 1 视角（与 `/camera/1/frame` 一致）。

### V6（P1）游戏指令/统一 capture 全参数贯通

- `ParamParser` 支持 `camera:<id>`；
- `/captureapi capture camera:2 filter:grayscale quality:90`：读相机 2 的帧＋滤镜覆盖；
- `/captureapi camera status` 输出每路 `lastFrameAgo`（最近一帧距今）；
- `help` 更新。

验收：一条指令同时指定 `camera:2`＋`filter`＋`quality` 生效。

### V7（P1）性能护栏

- `multi_camera_fps`×路数×编码耗时的护栏校验（超出预算告警日志，不硬拒）；
- `/health` 增加 `multi_rendered`/`multi_consumers`/`multi_last_frame_ms` 字段；
- 文档：`docs/多路视频流说明.md`（本计划落地后编写，含 0x04 格式表）。

## 四、实施顺序与依赖

```
V1（存储＋cameraId）→ V3（grabFrame 双模式，依赖 V1）
V1 → V2（WS 订阅，依赖统一存储）
V1 → V4（调度，依赖消费者信号）
V2+V3+V4 完成 → V5（录像）→ V6（指令贯通）→ V7（护栏/文档）
```

V1~V4 为一个交付批次（核心闭环）；V5~V7 为第二批次（增强）。

## 五、风险

| 风险 | 等级 | 应对 |
|---|---|---|
| 多路同帧渲染超预算（路数多时） | 高 | V4 帧预算硬顶＋懒渲染；超限告警不崩 |
| 0x04 与 0x01 并存期间客户端混淆 | 中 | magic 首字节分流；仅订阅连接收 0x04 |
| CameraFrameStore 内存（8 路×每帧~200KB） | 中 | 只存最新帧（已是 Map 单值）；路删除即 remove |
| 双写（Bus+Store）期间帧重复消费 | 低 | Store 幂等 put；消费者按 cameraId 判重 |
