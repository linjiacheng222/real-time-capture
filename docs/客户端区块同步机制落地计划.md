# 客户端区块按需同步机制——落地计划（T2.7.2-bis）

> 日期：2026-11-04。前置事实（S10 实测＋recomp.jar 反编译核验）：
> 1. `SingleplayerTicketHolder`（`5abdee8`）已让区块在**服务端**保持加载（日志 held=152），但客户端渲染需要的是**数据同步到客户端**——原版只同步玩家视距（12 区块）内的区块，相机 +200 格处服务端有数据、客户端 `ClientLevel` 里根本没有 `LevelChunk`，故画面只有视距重叠区（左下角）有内容。
> 2. 1.20.1 向客户端发区块的正式通道（已核验签名，位于 recomp jar）：
>    - `ChunkMap.updateChunkTracking(ServerPlayer, ChunkPos, MutableObject<ClientboundLevelChunkWithLightPacket>, boolean wasAdded, boolean wasRemoved)`（protected，可 AT/Mixin 提升）
>    - `ClientboundLevelChunkWithLightPacket(LevelChunk, LevelLightEngine, BitSet, BitSet)` 公开构造器
>    - `ClientboundForgetLevelChunkPacket` 用于卸载
> 3. 目标：**本模组独立的区块同步机制**——相机需要的区块由模组主动向集成服申请"同步给我"，不依赖玩家视距。

## 一、机制设计

### 数据流

```
CaptureChunkPlanner（视锥+声音范围求区块集合，已有）
        │ chunks
        ▼
SingleplayerTicketHolder（服务端保持加载，已有）
        │ 同一集合
        ▼
ChunkSyncRequester【新建·客户端】
  - 每客户端 tick 对比 desired vs synced
  - 未同步的区块 → 经 MinecraftServer.execute() 投递：
      ChunkMap.updateChunkTracking(player, pos, new MutableObject<>(), true, false)
        （wasAdded=true 即走原版完整路径：打包 LevelChunk+光照 → 发 WithLightPacket 给该玩家）
  - 相机不再需要的区块（离开集合）→ 发 ClientboundForgetLevelChunkPacket 卸载客户端缓存
  - 客户端确认：ClientLevel.getChunk(x,z, FULL, false) != null 即已到达（用收包回执判定）
```

### 关键决策

| # | 决策 | 理由 |
|---|---|---|
| D1 | 用 `updateChunkTracking(player,pos,mutable,true,false)` 而非手工构造包 | 走原版完整路径（含光照/BlockEntity/Forge hooks），零遗漏；它内部会对新区块构造 `ClientboundLevelChunkWithLightPacket` 并 `connection.send` |
| D2 | protected 方法 → 用 Access Transformer（`accesstransformer.cfg` 已存在为空模板）提升为 public | 项目已有 AT 基建；比 Mixin@Invoker 少一个类 |
| D3 | 卸载用 `connection.send(new ClientboundForgetLevelChunkPacket(pos))`，但**必须保守**：只卸载"不在相机集合**且**不在玩家视距内"的区块 | 防止误卸玩家正常区块 |
| D4 | 同步节奏：每 tick 最多入队 8 个新块（防带宽/卡顿尖峰）；集合不变则零操作 | 复用原版 sender 的背压思想 |
| D5 | 玩家自身移动导致原版 ChunkMap 重发/卸载时，与我们的 synced 集合可能竞争——用"desired 集合 = 摄制集合 ∪ 玩家视距集合"计算卸载，其余交给原版 | 竞争面最小化 |
| D6 | 远程 MP：本机制不适用（无集成服）——远程走 M9 通道（已有 RemoteCaptureClient），M9 服务端侧后续在 ChunkRequest 受理时同样调 updateChunkTracking 回发给申请玩家（这是 M9 后续任务，不在本计划内） | 单机/远程分治 |

## 二、任务分解

### CS1：AT 解锁＋ChunkSyncRequester 主体（P0）

- `src/main/resources/META-INF/accesstransformer.cfg` 追加：
  `public net.minecraft.server.level.ChunkMap m_140416_(Lnet/minecraft/server/level/ServerPlayer;Lnet/minecraft/world/level/ChunkPos;Lorg/apache/commons/lang3/mutable/MutableObject;ZZ)V`
  （执行端需用 unmapped SRG 名——构建时经 ForgeGradle 自动重映射；用 `javap -p` 反查 recomp jar 中 `updateChunkTracking` 的 SRG 名，或直接 Mixin@Invoker 备选）
- 新建 `src/main/java/com/captureapi/video/chunk/ChunkSyncRequester.java`：
  - `update(Set<Long> desiredChunks)`：由 `SingleplayerTicketHolder.update` 成功后调用（同一集合，紧随其后）；
  - 维护 `Set<Long> synced`；diff 出 toSend/toForget；
  - toSend：`server.execute(() -> { ChunkMap cm = serverLevel.getChunkSource().chunkMap; cm.updateChunkTracking(player, pos, new MutableObject<>(), true, false); })`；每 tick 限 8 个（内部队列消化）；
  - toForget：条件＝目标块 ∉ desired 且 ∉ 玩家视距（`ChunkMap.isChunkInRange(playerChunkX, playerChunkZ, cx, cz, serverViewDistance)`，public static 已核验）；发 `player.connection.send(new ClientboundForgetLevelChunkPacket(pos))`；
  - 玩家对象：单机＝`server.getPlayerList().getPlayers()` 中的本地玩家（集成服只有 1 人）；
  - 计数日志：`[CHUNK/SYNC] 入队=n 已同步=n 卸载=n`（沿用 TICKET 日志风格）。
- 接线：`CaptureChunkPlanner.capture()` 中 `SingleplayerTicketHolder.update(chunks)` 之后加 `ChunkSyncRequester.update(chunks)`。

### CS2：世界退出清理＋上限（P0）

- `WorldLifecycleHandler` 退出路径：`ChunkSyncRequester.releaseAll()`（synced 清空；ticket 释放已由 holder 做）；
- 上限：synced 集合 ≤ 2048（与 ticket 上限一致），超出 WARN＋截断；
- `/health` 增加 `chunk_synced` 字段。

### CS3：验证与证据（P0）

- 构建 24/24；
- dev 实测（脚本复用 `scripts/s10_fix_verification.py` 改造为 `s11_chunk_sync_test.py`）：
  1. 进世界 → 相机 +200 格水平朝玩家；
  2. 等待 60s（首帧＋同步窗口）；
  3. 断言①：日志出现 `[CHUNK/SYNC] 已同步=` 且数值 ≥ 视锥区块数的大部分；
  4. 断言②：HTTP `/camera/1/frame` 取帧，像素分析**画面下半 ≥60% 宽度出现非天空像素**（对比 S10 基线只有左下角局部）；用 ffmpeg signalstats：`非天空像素行占比`（逐行判断该行平均色偏离天空色 176,205,254 超过阈值 25）；
  5. 断言③：录像 12s（此时相机位同步后光照/方块就绪），帧内容有变化；
  6. 断言④：卸载验证——删除相机→等 10s→日志 `[CHUNK/SYNC] 卸载=n` 且客户端不再持有（无崩溃即可，深检可选）。
- 证据：`docs/evidence/S11/`（日志摘录＋帧 jpg＋像素分析 JSON＋断言结果）。

## 三、风险与边界

| 风险 | 应对 |
|---|---|
| updateChunkTracking 的 MutableObject 语义（null 时惰性构造缓存包）——同区块多玩家复用 | 单机仅 1 玩家，直接每次 new MutableObject |
| 客户端收到区块但渲染 Section 未重建 | 原版 handleLevelChunk 会自动 setSectionDirty；无需干预 |
| 玩家视距动态变化（options） | D5 的卸载判定每次实时读 serverViewDistance |
| 远程 MP 误启用 | 入口判定 `getSingleplayerServer()!=null`，与 holder 一致 |
| 大视锥一次性 297 块全部请求 → 带宽尖峰 | 每 tick 8 块限速，~37 tick≈2s 内同步完，可接受 |

## 四、验收定义（给用户看的最终标准）

游戏内建相机于**玩家 +200 格**、水平朝向，取帧：
- 画面下半部**大面积**出现地形（山体/树木轮廓），非仅左下角局部；
- 相机删除后区块卸载、无泄漏；
- 玩家正常视距体验无回归（自己周围照常）。
