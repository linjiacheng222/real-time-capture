# 网络音视频推流协议（T4.2）

> 状态：**T4.2 代码完成**（2026-10-31）；dev 运行时已验证 **WS 二进制音频块**（1784B = 20B 头 + 1764B PCM，10ms/441 采样）；视频帧因当前无 M4 控制指令创建相机，尚未在游戏内实推，编解码往返留测试分计划。
> 关联：I4.2.1~I4.2.5、I3.4.4 音频块契约、I2.5 JPEG 帧、I4.6 背压。

## 一、端点

| 出口 | 端点 | 说明 |
|---|---|---|
| MJPEG/HTTP | `http://127.0.0.1:25580/...` | 后续 T4.4/T4.5 |
| WS 推流 | `ws://127.0.0.1:25581/` | 本 T；token 开启时 `?token=` |

## 二、视频帧线格式（I4.2.1，16B 头，小端）

| 偏移 | 字段 | 类型 | 语义 |
|---|---|---|---|
| 0 | timestampNanos | int64 | 数据就绪时刻（与音频同一 CaptureClock 基） |
| 8 | width | int16 | 帧宽 |
| 10 | height | int16 | 帧高 |
| 12 | payloadLength | int32 | JPEG 字节数 |
| 16 | jpeg | bytes | JPEG 载荷 |

接收端校验 `payloadLength == 消息长度-16`，不符丢弃并计数。

## 三、音频块线格式（I4.2.2，20B 头，小端）

| 偏移 | 字段 | 类型 | 语义 |
|---|---|---|---|
| 0 | startNanos | int64 | 块起始（I3.4.1） |
| 8 | endNanos | int64 | 块终点（整数推算 I3.4.2） |
| 16 | sampleCount | int32 | 实际采样数 |
| 20 | pcm | bytes | PCM_SIGNED 16bit 小端交错 |

与 `AudioChunk` 字段一一对应（唯一契约源 I3.4.4）。

## 四、推送与广播

- 专用线程 `captureapi-push`：音频按拍从 `AudioRingBuffer` 读取（10ms 节奏），视频轮询 `VideoFrameBus` 最新帧（同帧只推一次）；无客户端时仍消费音频避免重连积压；
- 每连接私有有界发送队列（容量 32）+ 独立写线程；队列满 → 断开慢连接（1013）并计数（`/health` 的 `slow_disconnects`）；
- 推送线程永不阻塞渲染线程，也不因慢客户端阻塞其他客户端；
- 消息边界由 WebSocket 保证；应用层只做消息内长度自校验（I4.2.4）。

## 六、已知缺口

- 视频帧实推未测（无活跃相机；需 T4.3 控制指令或 M4 T4.7 临时相机后验证）；
- 多客户端一致性/慢连接断开/队列压测、Codec 随机载荷往返、接收端 Python 示例未执行；
- WS 接收端关闭握手（.NET 客户端 probe 在关闭阶段异常）待排查；不影响数据接收。
